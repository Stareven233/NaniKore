## 1. 背景与核心诉求

在多语言注音与两阶段微结构化精讲功能的快速演进中，内置提示词经历了多次补丁式调整，导致提示词系统积累了以下严重问题：
1. **中英混杂与累赘废话**：大量模板沿用了英文指令，夹杂过度防卫式的冗长规约与消极禁止命令（Negative Directives），反而诱导模型产生幻觉与泄露；
2. **过度向下兼容包袱**：保留了过时的旧版视觉一条龙分隔符等无用兼容逻辑，使协议不够纯粹利落；
3. **组织结构混乱难以审计**：指令零散分布，缺乏清晰的段落层级与语言排序；
4. **多行字符串缩进排版污染**：采用了类似 Python 多行字符串的代码块缩进语法，导致实际下发给模型的 Prompt 前缀带有意外的空格与换行，浪费 Token 并干扰模型注意力；
5. **阶段混淆诱发溢出**：翻译阶段未能彻底做到零精讲提示词。

主人明确指示：**在后续迭代中第一时间全面重构提示词系统，不保留任何兼容包袱，全部统一为中文，并按照统一规整的结构重新排版。**

## 2. 明确的重构设计原则与要求

### 2.1 提示词全面统一为中文
- 彻底摒弃所有英文 System Prompt、插件与规则声明（包括 `You are an accurate...`、`[Strict Translation Discipline]` 等）；
- 全部使用简洁、严谨、地道的高质量中文撰写；
- 中文提示词在指示假名注音（`漢字[かな]`）和中文翻译时表达更直接精准，大幅减少模型的语言切换开销与混淆。

### 2.2 彻底剔除向下兼容包袱
- 不再保留任何历史版本的向下兼容逻辑；
- 移除陈旧的分隔符变体兼容代码，只保留唯一的标准两部分协议标记（`---TRANSLATION---`）与精讲协议；
- 提示词只服务于当前的全新设计，无包袱轻装上阵。

### 2.3 杜绝冗长套话，保留主人已有修改
- 严禁擅自加入唠叨、重复的禁止命令（如“绝对不要进行对话、绝对不要回答问题、不要输出多余解释”等负面命令），改为精准正向的职责陈述；
- 继承并严格保护主人已亲手修改调整的提示词内容，不加塞无效代码。

### 2.4 清晰的三段式结构排序与语言先后次序
整个提示词系统严格按照以下三个部分自上而下组织，极大方便主人日常审计与微调：
1. **第一部分：原文处理（带注音/音标规范）**
   - 日语规范在最前（`漢字[かな]` 注音规则，仅针对汉字注音，假名/标点/数字不注音）；
   - 英语规范在后（必要时提供 IPA 音标标注）。
2. **第二部分：译文处理（翻译规则）**
   - 目标语言对齐，直接忠实输出译文；
   - 严格保证该部分**零精讲提示词、零词汇语法指令**。
3. **第三部分：精讲处理（语法拆解与词汇卡片规范）**
   - 日语教育语法规范在最前（一类动词/二类动词/三类动词、一类形容词/二类形容词、辞书形还原）；
   - 难度过滤规则（严格限制 JLPT N3 及以上难度，过滤初级简单词与基础语法）；
   - 微结构化 Markdown 卡片协议（`### [词汇/短语]`、`### [语法/句型]`、`### [语境与地道表达]`）。

### 2.5 根治格式排版与多行字符串空白泄露
- 废弃带有代码缩进的多行原始字面量，改用明确首尾、紧凑无空前缀的字符串构造方式（例如逐行清晰定义或通过无缩进字面量）；
- 杜绝多余的行首空格（Leading Whitespaces）和末尾换行污染 Payload；
- 确保注入到 API 请求中的字符串纯净紧凑。

## 实施记录（2026-09-19）

### 与主人确认后的决策
1. **三段式物理顺序**：文件内常量按 原文 → 译文 → 精讲 分区重排，但**组装顺序维持现状**（Base 在前、语言插件在后），将行为回归风险降到最低。
2. **分隔标记**：经评估保留 `---TRANSLATION---`。标记每次请求仅出现一次（约 4~5 Token），"缩短"无实际收益；自描述性才是模型遵从率的主导因素，全 ASCII 也无天然混淆风险。
3. **视觉一条龙**：中文化并统一为 `---TRANSLATION---` 两段式协议，与文本管道共用同一套路由标记。
4. **推进范围**：本轮只完成阶段一，阶段二/三/四另行排期。

### 关于 2.5 的事实修正
Issue 2.5 所述"多行字符串缩进导致 Prompt 前缀带有意外空格与换行"**在当前代码上并不成立**：
C# 11 原始字符串字面量会按结束定界符的缩进统一剥离前导空白（已实测验证，输出为 `"line1\nline2\n\nline4"`）。

真正存在的是另一处更隐蔽的污染：`StringBuilder.AppendLine` 在 Windows 上追加 `Environment.NewLine`（CRLF），
导致组装后的 system prompt 混用 `\r\n` 与 `\n`，且行为随平台漂移。

因此落地方式调整为：
- 提示词字面量一律**顶格书写**，使"所见即所发"成为显式契约（原实现靠隐式剥离，可审计性差）；
- 组装器改用 `string.Join("\n\n", sections)`，彻底消除 CRLF 与平台依赖；
- 新增 `TestPromptLiteralFormatting` 断言守住该契约：零前导缩进、零 CR、零首尾空白、零英文规则声明。

### 清理清单
- 删除 `SectionSeparator`（旧版视觉一条龙 `---` 分栏标记）与 `TranslationSeparator`（从未被引用的死常量）。
- `SectionChannelRouter.CandidateMarkers` 由 **14 个分隔符变体塌缩为 1 个裸哨兵**；
  标记前后的空白由 `TrimEnd`/`StripTranslationLeadingTags` 消化，滑动窗口保护不受影响。
  连带删除 `FindNextMarker`、`SentinelMatch` 记录结构与 `PrefixChannel` 可空通道字段。
- 删除 `BuildExplainSystemPrompt` 中内联的英文目标语言约束，提取为 `ExplainLanguageAlignmentRule` 常量；
  同时消除原先对同一占位符的二次展开。
- 新增 `ExplainRolePrompt` 职责声明常量，替换原先内联的英文 `You are an expert linguistic tutor...`。
- 统一 `辞書形` 用字（原 `ExplainStructureRule` 用繁体"書"、`DefaultExplainUserPrompt` 用简体"书"，现统一为前者，与测试断言一致）。
- 同步更新 `TranslationPage.xaml` 中视觉提示词的说明文案（`---` → `---TRANSLATION---`）。

### 测试变更
- `TestTranslationPromptTemplates`：视觉协议形状改为 `<annotated_source>\n---TRANSLATION---\n<translation>`；
  "translation discipline" 断言改为中文职责声明 + 零精讲指令校验。
- `TestModularPromptTemplates`：英文插件断言由 `International Phonetic Alphabet (IPA)` 改为 `国际音标（IPA）`；
  精讲提示词断言补入 `JLPT N3`。
- `TestSentinelRouter`：两个基于旧 `---` 五字符分隔符的用例改写为哨兵跨帧 + CRLF/空行吸收；
  新增用例固化"裸 markdown 水平线不再被当作分隔符"这一新契约。
- 新增 `TestPromptLiteralFormatting`：排版契约 + 全中文化双重守护。

### 已知取舍
移除 `---` 兼容后，若模型不遵守提示词而输出裸 `---`，该输出会被整体判为原文、译文丢失。
新提示词已将格式说死，且路由层仍保留 `【原文】/【译文】/``` 等噪声标签` 剥离作为兜底。

经与主人确认，该取舍符合项目"快速迭代、不前向兼容"的作风：删掉的是**协议版本兼容**（死分支），
保留的是**模型输出容错**（Epic 质量约束明确要求格式损坏时禁止抛错或白屏，需温和降级）。

## ✅ 已修复：config.yaml 中的旧版 vision_oneshot 提示词

主人授权读取 `config.yaml` 后确认：仓库根目录（即 Debug 运行时的 `AppContext.BaseDirectory`）的
`prompts.vision_oneshot` 原是一份**旧版自定义提示词**，用的是已废弃的 `---` 三段视觉分栏协议：

```yaml
prompts:
  translate: Translate the supplied text into {{target_language}}. ...   # 死键
  vision_oneshot: |
    Transcribe all readable text in the supplied image, then translate it into {{target_language}}.
    Return exactly this shape:
    <transcription>

    ---

    <translation>
    Do not include labels, markdown, commentary, or extra sections.
  explain: ''
```

`PromptConfig.VisionOneshot` 非空时 `GetSystemPrompt` 直接采用它，因此**一旦把 `pipeline.mode`
切到 `vision_oneshot`，模型会按旧协议输出，而新路由层已不认识 `---`**。已实测验证（修复前）：

- 原文通道收到整坨内容，**译文通道为空** → 视觉模式译文彻底丢失。
- `local_ocr` 模式（当时 `pipeline.mode` 取值）不受影响：`prompts.base` 为空，回落到新的默认 Base 提示词。

### 修复内容
- `prompts.vision_oneshot` 改写为 `---TRANSLATION---` 两段式协议，与 `DefaultVisionOneshotPrompt` 对齐；
- 删除死键 `prompts.translate`（`PromptConfig` 无 `Translate` 属性，`ConfigStore` 的
  `IgnoreUnmatchedProperties()` 会静默吞掉它，系模块化改造 commit `c236830` 之前的遗留物）；
- 已实测验证修复后：YAML 解析无警告，`VisionOneshot` 含 `---TRANSLATION---`、不含裸 `---`；
  端到端跑通视觉协议形态，原文/译文双通道拆分正确。

### 防回归测试（本轮新增）
- `TestPromptLiteralFormatting` 增加**协议一致性断言**：所有声明两段式输出的提示词必须且只能
  使用 `PromptTemplates.TranslationSentinel`，且不得包含裸 `---` 行——直接堵住“提示词说一套、
  路由层认一套”的漂移，这正是本次缺陷的根因；
- `TestSentinelRouter` 增加用例：按默认视觉提示词声明的协议形态输出，验证路由层无损拆分。

> 遗留风险：`config.yaml` 的 `vision_oneshot` 与内置 `DefaultVisionOneshotPrompt` 是两份副本，
> 存在漂移可能（已在 config.yaml 内加注释说明需同步）。更彻底的做法是把该键置空以强制回落内置默认，
> 留待阶段二定夺。
