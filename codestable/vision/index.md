# Vision

## 产品核心

NaniKore（何これ，"这是什么"）解决一件很窄的事：屏幕上出现看不懂的文字时，用最短的路径知道它说了什么，以及为什么这么说。

按下快捷键，画面冻住，框出那块区域，译文出现在选区下方。想再深入，点开精讲，看到关键词的读音、词性、在这个语境下的含义，以及整句为什么这样译。

目标体验的最小本质是**三秒看懂，三十秒学会**。前者要求从按键到译文全程不必思考、也不必离开当前画面；后者要求译文之外还有解释，让用户下次能自己认出来。这两件事共用同一次框选，但不共用同一条延迟预算：翻译必须快，精讲可以慢。

三个决定产品形态的取舍：

- **不打断。** 常驻托盘、无主窗口、不抢焦点。用户正在打游戏、看视频、读文档，NaniKore 的出现和消失都不该要求他先离开当前的事。
- **隐私是可选项，不是前提。** 默认走用户自己配置的 LLM API，简单直接；但整条链路必须允许全部替换为本机推理，让"数据不出本机"成为一个配置选择，而不是另一个产品。
- **译文是起点，不是终点。** 只给译文的工具已经很多。NaniKore 的差异在于愿意花第二次调用去解释，并且承认 OCR 会认错——所以原文永远可编辑、可重译。

## 用户旅程

**看不懂屏幕上的一段文字**（主旅程）

按快捷键 → 画面冻结 → 拖框选中 → 识别 → 译文浮现在选区下方。全程不离开当前窗口，ESC 随时取消。

**译文看懂了，但想知道为什么**

在结果卡片上点"精讲"，面板展开成文档：关键词逐条给读音、词性、此处含义；整句给结构拆解、为什么这样译、有没有别的译法。按需触发，不跟翻译一起自动发——既省等待也省 token。

**OCR 认错了一个词**

结果卡片里的原文可以直接改，改完重译。这是承认识别不可靠之后的必要出口，也是整个产品里性价比最高的一个功能：一次编辑救回一整句译文。

**文字本来就能选中，或已经在剪贴板里**

第二个快捷键直接翻译剪贴板内容，完全绕过截图和 OCR。网页、聊天窗口、代码注释适用，比框选更准。

**换一个翻译来源**

托盘菜单进设置，切换 provider：云端 API Key，或本机 llama-server / Ollama 暴露的 OpenAI 兼容端点。用户改一个 base_url 就从云端切到本地，不需要换版本、不需要重装。

稳定约束（这几条构成需求，不是示意）：

- 浮层显示的是**已冻结的位图**，不是实时画面。这既是交互需要（拖框时画面不能动），也是全屏游戏场景下唯一可靠的做法。
- 选区尺寸与放大镜在拖动过程中始终可见，用于对齐小字。
- 结果卡片**不抢焦点**，位置跟随选区；空间不足时翻到选区上方。
- 原文区域可编辑，编辑后可重新翻译。
- 翻译与精讲都**流式**呈现，首字尽早出现，不做整段等待。

## 能力版图

五个区域，前三个串成主旅程，后两个横向支撑。

**捕获**（屏幕 → 位图）。响应全局热键，抓取当前屏幕，输出一张带正确物理像素坐标的位图。这是整个产品技术风险最高的区域：多屏混合 DPI、硬件加速内容、HDR 色彩格式都在这里踩。深入读 `codestable/spec/index.md` 的架构考量。

**选区**（位图 → 矩形区域）。全屏无边框浮层，显示冻结画面，拖框、压暗、放大镜、ESC 取消。用户对这个产品的第一印象几乎全部由这个区域决定——它的手感就是产品的手感。

**识别**（图像 → 结构化文本）。调用 OCR 得到行级片段，重建阅读顺序拼成可翻译的文本。OCR 引擎本身是外部能力（现阶段由 leaf-ocr 提供），但**阅读顺序重建是 NaniKore 自己的核心逻辑**：多列排版、换行断词、中英混排的空格规则、行尾连字符合并。这一步的质量对最终译文的影响大于换一个更大的翻译模型。

**理解**（文本 → 译文 / 精讲）。两种能力共用一套 provider 抽象：翻译要求快、短、准；精讲要求结构、深度、可读。二者可以指向同一个模型，也可以分开配置。语言方向不由客户端检测，交给模型按指令判断。

**呈现与常驻**（结果 → 用户 / 应用生命周期）。托盘、热键注册、设置、结果卡片、精讲面板、剪贴板读写、配置与密钥存储。这个区域决定"不打断"这条产品原则能不能守住。

## 基础与边界

**平台。** 当前主目标为 Windows 10/11 x64。平台能力接缝（`Platform.Windows`）已系统性从业务核心切开，Linux/macOS 预留抽象接缝与跨平台数据格式头（实现另开事项）。

**形态。** 免安装便携目录：精简 Native AOT exe（`NaniKore.exe`，~20.8 MB）+ 随包原生 DLL 旁置 + 按需下载的 `deps/`。常驻托盘，无主窗口。不装服务、不进注册表启动项、不需要管理员权限。解压即用，目标机器零 .NET 运行时依赖。

**依赖姿态。** 运行期零 .NET / Python / WebView2 运行时依赖。本地 OCR 基于 `Microsoft.ML.OnnxRuntime` 直接执行 PP-OCRv6-small ONNX 模型，模型权重与 ONNX Runtime 原生库按需下载到 `deps/`（设置页可一键下载，亦提供带完整依赖的 `-full` 便携包）；图形渲染（SkiaSharp / HarfBuzz / ANGLE）与收藏持久化（SQLite）原生库随包旁置，主旅程开箱即用。

**密钥与数据。** API Key 用 Windows DPAPI 加密后存 `程序目录\.data\keys.bin`（带格式方案版本头，为跨平台留位），不落明文、不进日志。截图只在内存传递，不落盘（除用户显式保存）。收藏知识库保存在 `程序目录\.data\collections.db`。用户没主动开启时不上报任何遥测。

**技术上做不到的（不是待实现，是边界）：**

- **独占全屏（exclusive fullscreen）游戏**无法截取，也无法在其上覆盖浮层。游戏接管显示输出后 DWM 不在链路上，DXGI duplication 失效，任何置顶窗口都会把游戏踢出独占模式并触发最小化。Windows 11 上微软自己的截图工具同样如此。唯一的技术出路是注入游戏进程 hook D3D，会触发反作弊，**明确不做**。产品的应对是识别到这种情况时提示用户切换到无边框窗口模式——Win10 之后大量游戏被系统透明提升为 Fullscreen Optimizations（翻转模型无边框），这类正常工作，且官方说法是性能与独占全屏基本等同。
- **DRM 保护内容**（流媒体播放器等使用 `WDA_EXCLUDEFROMCAPTURE` 或受保护输出路径的画面）截取结果为黑，设计如此，不可绕过。

**明确不做的（有意排除，不是没想到）：**

- 竖排文本的阅读顺序重建。用户实际场景以横排为主，留作后续改进。
- 图片上的原位译文覆盖（把译文画回原文位置）。视觉上很吸引人，但要求精确的背景擦除和字体匹配，收益远低于成本。
- 批量翻译、文档翻译、翻译记忆库、术语库管理。这些是 CAT 工具的领域，与"三秒看懂"是不同的产品。
- 实时字幕 / 连续翻译（持续监视某个区域自动重译）。有价值但会彻底改变功耗、延迟与交互模型，属于探索空间而非当前目标。
- 语音朗读。

## 探索空间

- **连续翻译 / 实时字幕**：意图状态 `探索中`。盯住一个区域，内容变化就自动重译，用于游戏对话和视频字幕。与当前"一次框选一次结果"的模型并存但不互斥；难点在变化检测、去抖动和成本控制，而不在翻译本身。
- **本地 OCR 内嵌（去掉 Python）**：意图状态 `已实现`。C# 进程通过 `Microsoft.ML.OnnxRuntime` 直接加载 PP-OCRv6-small ONNX 模型，从 `deps/` 按需动态装载，完全摆脱 Python、OpenCV 与外部服务。
- **单文件体积指标**：意图状态 `已调整`。经 Epic 002 实测裁决，放弃单文件内嵌与解压开销，调整为「精简 Native AOT exe + 随包原生 DLL 旁置」，体积指标转为记录值，优先保证零运行时依赖与解压即用。
- **Windows.Media.OCR 作为零依赖兜底**：意图状态 `探索中`。系统自带，免费给词级边界框，可作为 OCR 端点不可用时的降级路径。
- **精讲用独立模型**：意图状态 `候选`。若本地 Hy-MT2 证实只擅长翻译、不擅长解释，则翻译走 Hy-MT2、精讲走另一个通用模型。provider 抽象已为此留口，但是否值得让用户配两个模型待定。
- **精讲结果本地留存 / 生词本**：意图状态 `已实现`。已由 Epic 001 落地，SQLite 收藏服务本地持久化至 `.data/collections.db`，支持设置面板分类浏览、检索、快速复制与批量管理。
- **结果面板改用 WebView2**：意图状态 `放弃`。精讲微结构化卡片与假名振假名已由 Avalonia 12 FluentTheme 原生控件树完美承载，性能高效且完全零 Webview 依赖。
- **译文原位覆盖**：意图状态 `放弃`。理由见「基础与边界」。。

## 统一语言

- **捕获（capture）**：从屏幕取得位图的动作。不要和"截图"混用——后者在用户语境里常指"存成文件"，而 NaniKore 默认不落盘。
- **选区（selection）**：用户框出的矩形，以物理像素与虚拟桌面坐标表达。不是"截图区域"，因为它作用在已冻结的位图上。
- **冻结画面（frozen frame）**：捕获瞬间的那一帧位图，浮层显示的全部内容。强调它是静止的，与实时画面不同。
- **翻译（translate）** 与 **精讲（explain）**：两种不同的理解能力，延迟预算、输出形态、触发方式都不同。不要合称"翻译功能"。
- **provider**：一个可替换的外部能力端点（OCR provider、翻译 provider、精讲 provider）。云端与本机的区别只是配置，不是不同的产品形态。
- **阅读顺序重建（reading order）**：把 OCR 的行级片段拼成连贯文本的过程。不要叫"文本拼接"，那低估了它的分量。
- **独占全屏 / 无边框全屏**：两者行为完全不同，前者是技术边界，后者正常工作。谈全屏问题时必须区分，不能只说"全屏"。
