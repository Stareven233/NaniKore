# 学习型功能演进与精讲假名收藏设计 talk

> 本 talk 记录 2026-09-18 针对 NaniKore 向语言学习工具演进的交互与架构讨论，按实际研讨与纠正节拍组织。

---

## 1. 原始意图与真问题

**用户的开场原话：**
> 本项目目前实现了基本功能，目前支持本地ocr识别然后远程llm整句翻译，后续我希望增加翻译精讲、日语分词、假名标注、知识点（单词？短语？语法？）收藏等功能，往学习类应用的方向迭代，但目前有几个问题：
> 1. 不知道怎样设计UI/交互来呈现这些功能
> 2. 个人主要应用场景是日语->中文，优先确保，但同时也希望兼容其他语言

**真问题：**
NaniKore 的核心定位是“三秒看懂，三十秒学会”。用户需要的不是一个沉重庞大的词典查词软件，而是在桌面任意窗口（游戏、网页、文档）中，**零打断地完成从“扫清生词障碍”到“随手沉淀高价值语言知识点”的学习闭环**。
技术重心的转变：从单纯的“OCR 文本重构与翻译流水线”，延伸为**“富文本假名排版、两阶段缓存复用、微结构化知识提炼与轻量便携持久化”**。

---

## 2. 原文区交互：假名（Ruby）阅读与编辑的冲突与化解

**冲突点：**
WPF 的原生 `TextBox` 是纯文本控件，无法进行上下双层的振假名（Ruby）排版；而支持注音富文本排版的控件通常为只读，与“OCR 认错字时用户必须能随手修改重译”的底线原则相冲突。

**推演与关键定夺：**
- **排版载体**：采用自定义的 `FlowDocumentScrollViewer`，汉字上方排布注音小假名；
- **拖选与复制体验**：在只读假名视图下，鼠标拖选不仅支持直接选择复制汉字原文，也支持拖选复制注音假名；同时右键菜单提供快捷项：`复制纯日文`、`复制带注音文本`（`汉字[假名]` 格式）、`复制假名读音`；
- **双击无缝切换编辑**：默认以精美假名阅读态呈现；**用户双击原文区**立即原地切换为纯文本 `TextBox`（自动选中文本并聚焦），修改完成后失去焦点或按 Enter 自动切回假名阅读态并支持重译。

**已确认：** 原文区采用“默认 FlowDocument 假名排版（支持假名/日文拖选及右键复制）+ 双击切换纯文本 TextBox 编辑”的交互方案。

## 3. 请求阶段与会话复用（Prompt Cache 优化）

**分歧与权衡：**
一次性把假名、翻译、单词、短语、语法全部让大模型返回（One-shot），还是分阶段请求？

**推演与纠正：**
- 一步到位会导致用户只想看一眼翻译时也必须承担漫长的 Token 等待与多倍调用开销；
- 采用**两阶段分离**：
  - **阶段 1（翻译与注音）**：截图后触发，LLM 流式输出带假名的原文与中文译文。格式极简（纯文本标记分隔），0 延迟、0 解析失败率；
  - **阶段 2（深度精讲）**：用户按需触发，LLM 输出词汇、短语、语法剖析与地道表达。
- **主人关键决策**：阶段 2 发起请求时，**必须复用阶段 1 的上下文 Session 历史**（`messages` 携带阶段 1 的输入输出）。这样可以命中主流模型提供商（Claude、OpenAI、Gemini 等）的 **Prefix Prompt Caching 机制**，不仅节约 80%+ 的输入 Token 开销，还能保持上下文一致性。

**已确认：** 两阶段解耦；阶段 2 复用阶段 1 的对话历史以命中 Prompt Cache。

## 4. 精讲触发入口与面板展开

**选项：**
顶部工具栏按钮、译文行独立按钮，还是底部折叠栏？

**已确认：**
采用结果卡片最底部的 `Expander` 折叠面板，文案为 `[ 📖 精讲与语法解析 (点击展开) ]`。**“底部展开即触发”**：用户点击展开时才发起第二阶段请求并流式打字；已生成过的内容再次折叠与展开不重复请求，保持界面最轻量。

## 5. 精讲卡片化、一键收藏与容错降级

**疑虑与突破：**
严格的 JSON 输出无法良好流式渲染，且大模型容易格式翻车；纯 Markdown 则难以精确提取词汇信息存入生词本。

**推演与主人的补充约束：**
- **混合模式（方案 C）**：
  1. **微结构化卡片流**：LLM 遵循行规约输出词汇与语法条目，前端正则边流式接收边识别为独立的小条目卡片，卡片右侧提供 `[★ 收藏]` 按钮，一键收集“原词、读音、原形、语境释义、原句上下文”；
  2. **正文划选收藏**：用户在精讲富文本中亦可任意拖选文本，弹出气泡让用户自主选择类型（单词 / 短语 / 语法 / 备注）进行收藏；
- **错误处理与降级**：若大模型偶发未遵循标记格式，**严禁崩溃或界面空白**。客户端通过 `StatusBar` 通知用户“未能完全识别结构化卡片，已展示原始排版”，并将大模型输出作为完整 Markdown 优雅渲染。

**已确认：** 微结构化卡片（带 `[★]` 按钮）+ 自由划词选择类型收藏；模型格式异常时提示并降级原样展示。

## 6. 生词库形态与数据持久化

**宿主与功能：**
- 放弃独立的悬浮/停靠面板以控制复杂度；在现有的 `SettingsWindow` 中新增一个独立的 **`[收藏]`** Tab，未来随设置面板一同作为主管理面板；
- 第一期实现**轻量查阅与整理（MVP）**：支持类型过滤（全部 / 单词 / 短语 / 语法）、关键字搜索、单条删除、一键复制。

**存储方案定夺：**
- 选用 **SQLite**；
- 数据库文件保存在**程序运行目录**（与 `deps/`、`config.yaml` 同级），单文件绿色便携；
- 采用**运行时首次收藏时才惰性创建并写入**的策略，软件解压更新覆盖时绝不影响用户的本地数据库资产。

**已确认：** 设置面板内置 `[收藏]` Tab；根目录 SQLite 惰性建库持久化。

## 7. 多语言提示词架构与现代文法精简

**语言探测与动态拼接：**
- 客户端在 OCR 文本产出后进行轻量字符集探测（毫秒级判断是否包含平假名/片假名、拉丁字母等）；
- 采用 **Base Prompt（流式分隔符与格式约束）+ 语言特化插件** 拼接组装。若遇日英混合句子，自动将涉及的语言特化规则同时拼入；
- 各语言提示词在配置中对用户完全开放自定义；
- 无论源语言为何，精讲、词汇释义必须强制与当前设置的 `target_language` 保持一致。

**主人的关键纠正（现代实用文法导向）：**
- **坚决摒弃生硬繁琐的日本传统学校文法术语**（如“未然形”、“连用形”等已过时且对理解无实际帮助的称谓）；
- 日语重点只提取：**假名注音 + 动词原形（辞书形）**；
- 英语重点只提取：**国际音标（IPA）+ 动词原形**。

**已确认：** 客户端字符集探测 + 模块化提示词拼接（支持混排）；提示词模板可配置；强制目标语言一致；文法注解严格聚焦于“注音/音标 + 原形”。
