# 目标语言感知提示词门控与质量优化 talk

> 本 talk 记录 2026-09-23 围绕 `PromptTemplates.cs` 的提示词体系优化研讨。按实际对话与推演节拍组织，收敛了插件门控对目标语言的语义剪枝、规则与示例自洽、Base 混排纪律以及精讲排版等四个维度的决策与建议出口。

---

## 1. 原始意图与主人的核心洞察

**主人的开场原话：**
> 当前提示词是否有需要优化的地方，请给一些建议。比如我突然想到里面列了一些对输入语言的特殊处理，但如果该语言就是目标语言（比如翻译成英语，但输入中混有英语部分），此时没必要对该语言进行翻译、解读，相关提示词也就没有必要注入。

**真问题与现象剖析：**
主人的洞察触及了当前提示词架构中的一个重大设计盲区——**插件门控是纯“源文本视角”的，完全未感知“目标语言（Target Language）”**：
1. **日译英混排场景下的噪点注入**：
   - 假设输入为 `Nintendo Switchの最新ゲームをプレイする`，目标语言设为 `英语`。
   - 当前 `LanguageDetector` 扫描到拉丁字母即标记 `HasEnglish = true`，导致 `PromptTemplates.AppendLanguagePlugins` 强行将 `EnglishPlugin`（IPA 音标规范）注入 System Prompt。
   - 用户的目标产物本来就是英语，在日文原文中为 `Nintendo Switch` 标注音标不仅毫无学习价值，还会给大模型带来干扰（误以为要对常见英文商标注音）。
2. **潜在中/英译日的假名污染**：
   - 目标语言为日语时，若源文本中存在引述假名，也会无条件触发 `JapanesePlugin`，甚至诱导模型把中文汉字按日文汉字标注假名。

**已确认原则：**
语言特化插件（`JapanesePlugin` / `EnglishPlugin`）的本质定位是**“为源语言的学习者提供生词阅读辅助（振假名 / 音标）”**。一旦某种语言就是最终的**目标语言**，该插件对源文本的辅助功能即告失效，绝不应当注入。

---

## 2. 插件门控的语义剪枝与 Prompt Cache 影响推演

**门控剪枝方案推演：**
在 `PromptTemplates.AppendLanguagePlugins`（或 `LanguageDetector`）层建立目标语言互斥约束：
- 当 `TargetLanguage` 为英语（`IsEnglish(targetLanguage)`）时：**绝对不注入 `EnglishPlugin`**；
- 当 `TargetLanguage` 为日语（`IsJapanese(targetLanguage)`）时：**绝对不注入 `JapanesePlugin`**；
- 目标语言为中文时保持现状（中文原本即无注音插件，且纯汉字日文推断已有日译中偏好兜底）。

**视觉一条龙（Vision Base）的同步演进：**
- **现状**：视觉路径目前为了前缀缓存恒定同拼两个插件（`[VisionBase, JapanesePlugin, EnglishPlugin]`）。
- **推演**：视觉路径同样应当根据配置的 `TargetLanguage` 过滤掉同语种插件。
- **缓存影响定夺**：用户的 `TargetLanguage` 是全局设置项，一次设置后在会话周期内是静态恒定的。在特定的目标语言下，视觉 Prompt 仍然是**唯一的单变体**，**前缀缓存（Prompt Cache）命中率依然保持 100%**，同时彻底杜绝了日译英图片中英文被乱注音的问题。

**文本翻译路径的缓存变体收敛：**
- 剪枝前：文本路径存在 4 种变体（Base, Base+J, Base+E, Base+J+E）；
- 剪枝后：当目标语言为英语时，变体收敛为 2 种（Base, Base+J）；当目标语言为日语时，变体收敛为 2 种（Base, Base+E）。变体数量大幅减少，前缀缓存命中概率反而显著提升。

**已确认：** 插件门控引入目标语言互斥；文本与视觉路径均在目标语言重合时剔除对应插件；前缀缓存变体得到有效收敛。

## 3. 插件规则与示例自相矛盾的排查与修正

在代码走查中发现，当前两个语言插件的提示词存在严重的“Few-shot 覆盖规则”缺陷，导致大模型在实际执行时忽略难度门槛：

### (1) 日语插件（`JapanesePlugin`）
- **现行缺陷**：
  ```text
  [日语注音规范]
  对 JLPT N3 及以上难度的日本汉字标注振假名，格式为 漢字[かな]（例：私[わたし]は 学生[がくせい]です。）
  ```
  规则声称只标注「JLPT N3 及以上」，示例却标注了 **JLPT N5** 最基础入门汉字 `私` 和 `学生`。大模型倾向于优先模仿示例行为，导致无差别给所有汉字注音，产生满屏假名噪音。
- **优化定夺**：
  示例更换为真正的 N3+ 汉字（如 `挨拶[あいさつ]`、`躊躇[ちゅうちょ]`），并显式补充负向抑制：“日常基础汉字（如 私、学生、今日）严禁标注”。

### (2) 英语插件（`EnglishPlugin`）
- **现行缺陷**：
  ```text
  [英语音标规范]
  为原文中拉丁字母拼写的少见、困难单词用方括号标注国际音标（IPA），如 apple[ˈæpl]
  ```
  规则要求标注「少见、困难单词」，示例却是幼儿级单词 `apple`。同时缺乏对品牌名、缩写及代码变量的防护，导致模型容易对 `API`、`GitHub`、`dog` 乱打音标。
- **优化定夺**：
  示例更换为真正的高难生词（如 `ubiquitous[juːˈbɪkwɪtəs]`），并明确排除常见基础词、专有名词与技术缩写。

**已确认：** 修复两个插件“规则高门槛、示例超低幼”的矛盾，统一通过高难度正例与明确负向抑制规范注音密度。

## 4. Base Prompt 混排边界与过度翻译抑制

**背景痛点：**
`DefaultTranslationBasePrompt` 当前包含“所有的输入都是需要翻译的文本”字样，且缺少对混排文本中已有目标语言部分的行为指引。下游流式路由器 `SectionChannelRouter` 亦被迫维护大量前导噪声标签（如 `【原文】`、`【译文】`）的剥离状态机。

**优化方案：**
1. **混入目标语言的处置原则**：
   补充明确指引：“若原文中已有部分词句属于{{target_language}}（如专有名词、已为目标语言的短语），在译文中直接保留或自然融入，无需生硬二次转译；若整段已是{{target_language}}，忠实呈现即可”。
2. **无注音规范时的行为兜底**：
   补充指引：“若原文中无需注音或无对应注音规范，第一部分直接输出原始文本即可”。
3. **源头抑制流式标签噪声**：
   在 Base 中显式强调：“严禁输出诸如【原文】、【译文】等前缀或 Markdown 代码块标记，直接从第一部分内容开始输出”，从源头减少模型的格式幻觉，降低首字延迟（TTFT）。

**已确认：** 补充混排保留指导、无注音兜底说明与前导标签负向抑制。

## 5. 精讲 Prompt（`DefaultExplainUserPrompt`）的针对性与排版加固

**现存问题：**
1. 文案末尾的 `注：...若是英语则只挑选CET-6及以上难度的` 属于中国大学英语考试概念，通用 LLM 对 CET-6 的边界理解模糊，且源语言非英语或目标语言非中文时表述突兀；
2. Markdown 表格模板 `**词汇** | 假名读音或IPA | 词性 | 详细释义...` 缺少表头分割线声明，容易被小模型生成为破损的伪表格。

**优化建议：**
- 难度标准泛化为中高级（如“进阶/中高级重点词汇（六级/B2及以上）”）；
- 规范化 Markdown 结构，明确输出为完整标准表格或清晰列表，防止前端渲染崩塌。

## 6. 候选质量特征扫描 (ISO/IEC 25010)

- **功能适用性 (Functional Suitability)**：
  - *完备性与正确性*：彻底解决目标语言为英语/日语时的反客为主注音噪点；杜绝混排文本已有目标语言的过度转译；
- **性能效率 (Performance Efficiency)**：
  - *时间特性 (Time Behaviour)*：源头抑制前导标签减少首字等待；插件剪枝减少 System Prompt 长度；
  - *资源利用率 (Resource Utilisation)*：变体数量收敛（4 变体 $\rightarrow$ 2 变体），提升 LLM Provider 端的前缀缓存命中率；
- **可维护性 (Maintainability)**：
  - 提示词规则与示例逻辑自洽，降低未来调优和回归的心理负担。
