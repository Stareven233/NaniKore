# 截图 OCR 翻译工具选型与边界 talk

## 原始想法

用户的原话（2026-08-05，空目录起步）：

> 一个支持 windows 系统的截图 OCR 翻译工具。平时收纳于系统托盘，按下快捷键后，支持框选当前屏幕内容进行 OCR 识别（OCR 通过调用本地 API 接口的方式实现，传入图片得到识别的文本，相应项目我已经写好：D:\Code\projects\leaf-ocr），然后将结果翻译为中文（最好有个解释模式，进一步讲解为什么这么翻译，某个单词什么含义），翻译部分预计通过本地部署 Hy-MT2-7B/Hy-MT2-1.8B 量化模型实现，由于挺麻烦的，也希望能支持 API Key 的形式调用 LLM。在实现语言上，我更倾向 go，小巧精致，rust 的中间产物太庞大了。

补充的关键场景（第二轮）：

> 确实这个项目浮框选区很关键，尤其是我希望在游戏或视频场景中（全屏）使用。

## 真问题

用户要的不是"又一个划词翻译"，而是**在不打断当前活动（尤其是游戏和视频）的前提下，看懂屏幕上任意一段文字，并能理解它为什么这样译**。

这个定位把技术重心放到了两个不显眼的地方：一是全屏场景下的捕获与浮层（决定产品能不能用在主场景），二是 OCR 碎片到可翻译文本的重建（决定译文质量的上限）。翻译模型本身反而是风险最低的部分。

## 术语

沿用 `codestable/vision/index.md` 的「统一语言」，本 talk 不另立术语。特别注意 **独占全屏 / 无边框全屏** 必须区分，两者行为完全不同。

## 已确认决策

**语言选 Go。** 用户偏好，理由从"编译产物小"修正为"**省的是运行时依赖**"——最终是单文件、无 .NET / Python / WebView2 运行时。子 agent 在本机实测（go1.25.5, `CGO_ENABLED=0`, `-s -w -H=windowsgui`）确认托盘 + 热键 + 剪贴板空壳 2.0MB、Gio 空壳 2.9MB，加内嵌 CJK 字体后成品预估 8–12MB。同时诚实记录：C#/WPF 在捕获、透明窗口、富文本三件事上都是现成 API，工作量明显更小，代价是 120–160MB 自包含体积；Rust+egui 能到 2.5MB 但浮层同样要手写。Go 是两者之间的合理点，不是唯一正确解。

**不区分主力语向，语言判断交给 LLM。** 用户判断 PP-OCRv6 能同时识别中英日，LLM 本身能按指令灵活处理语向。客户端因此不做语言检测，prompt 里写"译为中文，若原文已是中文则译为英文"，面板留手动覆盖。省掉一整层逻辑。竖排文本不做，用户场景以横排为主。

**先 API Key，本地部署留口。** 用户明确要先用 API Key 测试。关键认识：这不是"把本地推迟了"——只要 provider 按 OpenAI 兼容 `/v1/chat/completions` + 流式实现，llama-server 和 Ollama 暴露的就是同一个接口，用户改 base_url 即切本地（官方已有 `tencent/Hy-MT2-1.8B-GGUF`）。顺带兼容 DeepSeek、智谱、SiliconFlow、OpenRouter。

**翻译与精讲是两个 provider 槽，v1 指向同一个。** 这里纠正了用户的一处判断：用户认为"Hy-MT2 原本就是 LLM 所以能讲解"，但 Hy-MT2 是在翻译数据上专门微调的模型，这类模型的通用指令跟随能力通常被牺牲（上一代 Hunyuan-MT-7B 的模型卡就是固定翻译模板）。是否能讲解**未能验证**（arXiv 与 GitHub 均被网络策略拦截）。选了先走 API 后此风险自动推后，但要留的口子是反向的：将来接本地 Hy-MT2 时它可能只能填翻译槽，精讲需另找模型。

**先连现成 leaf-ocr，发布时再内嵌。** 用户选择。最快端到端跑通，OCRProvider 抽象好之后改发布形态不用重写。

**精讲走流式 Markdown，不走 JSON。** 词条卡片看似需要结构化输出，但 JSON 流式解析脆弱，模型跑偏则整个面板空白；Markdown 边流边渲染，坏了只是排版丑。翻译走纯文本流式。

**原文可编辑可重译。** 承认 OCR 会错。一次编辑救回一整句译文，是全产品性价比最高的功能。

**精讲按需触发，不与翻译一起自动发。** 省等待也省 token。

**结果先用选区下方小浮卡，点精讲才展开大面板。** 精讲是长文档，塞进 tooltip 是错的。

## 约束

- 只做 Windows 10/11 x64；跨平台不是目标。
- 单文件可执行，常驻托盘，无主窗口，不需要管理员权限，不装服务。
- 运行期不捆绑 .NET / Python / WebView2 运行时。
- API Key 用 Windows DPAPI 加密存 `%APPDATA%\NaniKore\`，不落明文、不进日志。
- 截图默认不落盘。用户未主动开启时不上报遥测。
- 结果窗口不抢焦点（"不打断"是产品原则，不是优化项）。
- 第一天就上 PerMonitorV2 DPI 感知 manifest（go-d3d 要求，也是混合 DPI 坐标漂移的解法）。

## 影响面、风险与取舍

**全屏场景的真实边界（已查证，不需再调研）。** 独占全屏游戏既无法捕获也无法覆盖浮层：游戏接管显示输出后 DWM 不在链路上，DXGI duplication 返回 `ACCESS_LOST`，任何置顶窗口会把游戏踢出独占模式并触发最小化。Win11 上微软自己的截图工具同样失效。唯一技术出路是注入进程 hook D3D，撞反作弊，不做。

缓解面比听起来大：Win10 之后大量声称独占全屏的游戏被系统透明提升为 Fullscreen Optimizations（翻转模型无边框），这类走 DWM 合成，捕获与浮层均正常；视频播放器、浏览器视频、无边框窗口模式也都覆盖得到。真正打不到的是 DX9 时代或显式退出 FSO 的老游戏。官方说法是 FSO 性能与独占全屏基本等同，所以"请切无边框"的提示代价很低。

另一条硬边界：DRM 保护内容（`WDA_EXCLUDEFROMCAPTURE` 等）截取为黑，设计如此。

**捕获方案的主次因这个场景而反转。** 游戏/视频是主场景 → DXGI（`kirides/go-d3d`，纯 Go）是**主路径**，GDI（`kbinani/screenshot`，`BitBlt(SRCCOPY)`）降级为兜底。GDI 看不到 DirectComposition 层，在硬件加速的浏览器视频和全屏游戏里必黑。反过来 DXGI 也有已知失效场景需要 GDI 兜底：RDP 会话、Win11 竖屏显示器持续 `ACCESS_LOST` 的报告、部分虚拟机。HDR 模式下 duplication 固定返回 B8G8R8A8，需 `DuplicateOutput1` 显式声明 FP16 格式，这是已知会踩的坑。`ACCESS_LOST` 要当常规事件处理（释放帧、重建 duplication、短重试），不能当致命错误。

**"先冻屏再显示浮层"从省事升级为救命。** 浮层显示的是已截好的位图，即使游戏在浮层背后被踢出全屏，用户视觉上看到的仍是冻住的那一帧，框选照常完成。被打扰的是游戏，不是用户的操作。这也顺带绕开了 WebView2 长期未解的透明窗口黑屏问题——因为根本不需要窗口透明。

**OCR 输出是碎片，不是句子。** leaf-ocr 的 `/ocr` 返回 `texts[]` + `boxes[]`（见 `d:\Code\projects\leaf-ocr\app\main.py` 的 `/ocr`、`app\ocr_engine.py` 的 RapidOCR 封装）。直接 `join` 会在多列排版、换行断词、竖排文本上翻车，而这一步对译文质量的影响**大于**换一个更大的翻译模型。阅读顺序重建是 NaniKore 自己的核心逻辑，不是调 API 就有的。

**本地推理的延迟现实。** 本地 7B Q4 纯 CPU 出一句译文约数秒，对"按键即看到"偏慢。本地路线甜点是 1.8B（约 1.2GB），7B 属于"有显卡且要质量"档，云端 API 反而延迟最稳。provider 从第一天按流式设计，不要等精讲吐长文本时才回头改。

**待验证项（不是风险，是第一次跑通时顺手确认的事）。** leaf-ocr 现在用 `RapidOCR()` 默认配置。PP-OCRv6 官方说法：medium/small 档覆盖 50 语种含日文，tiny 档恰好排除日文。默认加载的 rec 模型字典里是否含日文假名**未验证**；若日文识别不行，需要改 leaf-ocr 侧的模型配置。

**技术选型的实测结果（子 agent 在本机编译验证，非搜索推断）。**

| 用途 | 选择 | 状态 |
|---|---|---|
| 托盘 | `energye/systray` v1.0.3 | CGO-free；getlantern 版停更三年多且拖着已死的 lxn/walk |
| 全局热键 | `golang.design/x/hotkey` v0.6.1 | Windows 纯 syscall；修饰键组合可用 |
| 剪贴板 | `golang.design/x/clipboard` v0.8.0 | CGO-free，支持图片 |
| 浮层 + 面板 | Gio v0.10.1 | CGO-free，空壳 2.9MB |
| 捕获主路径 | `kirides/go-d3d` v1.0.1 | 纯 Go DXGI，要求 PerMonitorV2 |
| 捕获兜底 | `kbinani/screenshot` | CGO-free（非 darwin） |

排除项：Fyne（需 CGO + MinGW，实测 `CGO_ENABLED=0` 直接构建失败）；`robotn/gohook`（需 CGO，且低级键盘钩子易被杀软误报）；`lxn/win`（2021 年后无更新）。

`RegisterHotKey` 是系统级独占，冲突时必须把错误显示给用户，不能吞掉。

**Gio 与 WebView2 的取舍（当前保留分歧）。** 精讲本质是富文本文档——分区、折叠、逐词高亮、选中复制，Gio 里全要自己搭，且 Gio 不自带 CJK 字形（需内嵌 Noto Sans CJK，注意 Han 统一导致中文字形出现在日文文本里会被母语者看出问题）。WebView2 白送字体回退与文本选中，但 Wails v3 仍是 beta.3，且 Win10 上 WebView2 运行时不一定预装。

决定：v1 用 Gio 做朴素面板，把面板与核心逻辑的边界切干净；若精讲 UI 真长成文档再单独替换面板。这是可逆的。

**已知未能验证的事项。** GitHub、pkg.go.dev、arXiv 在本次调研中被网络策略拦截。以下为搜索推断而非直接确认：WebView2 透明窗口问题、Fyne 的 CJK 字体 bug 历史、Hy-MT2 的精讲能力与 prompt 模板、C#/Rust 各栈的成品体积。Go 侧的 CGO 与体积数据是本机实测，可信。

## 候选质量目标

- **性能效率（时间行为）**：
  - 候选目标：热键按下到冻结画面显示 ≤ 150ms（用户感知为"立即"）；框选完成到译文首字出现，云端 provider ≤ 2s。
  - 依据：产品核心承诺"三秒看懂"；捕获慢会让用户以为热键没生效而重复按键。
  - 待决策：本地 provider 的目标值待实测 1.8B 后再定，不与云端共用一个阈值。
  - 候选证据：穿刺阶段打点记录各段耗时。

- **功能适合性（功能正确性）**：
  - 候选目标：多屏混合 DPI 下，选区映射到位图的物理像素矩形零偏移。
  - 依据：坐标漂移会导致 OCR 截到错误区域，且症状隐蔽（识别出的是隔壁的字）。
  - 候选证据：主屏 150% + 副屏 100% 的实机验证，含负坐标副屏。

- **可靠性（容错性）**：
  - 候选目标：捕获失败（`ACCESS_LOST`、DRM 黑屏、独占全屏）时给出可操作提示而非静默失败或崩溃。
  - 依据：这些场景在主用户场景里必然发生，用户需要知道是"切无边框"还是"这内容受保护"。
  - 待决策：黑屏检测的判据（纯黑占比阈值？）与提示文案。

- **信息安全性（保密性）**：
  - 候选目标：API Key 经 DPAPI 加密落盘；日志与错误信息中不出现 key 或截图内容。
  - 依据：用户自带 key，泄露代价直接是钱。

## 分歧

- 精讲面板最终是 Gio 自绘还是 WebView2 —— v1 用 Gio，替换条件（"Gio 明显吃力"）尚未量化。
- 本地 Hy-MT2 能否承担精讲 —— 未验证，等真正接本地 provider 时决定是否需要第二个模型。
- 独占全屏的降级提示做到什么程度 —— 是否值得检测"当前前台窗口是独占全屏"，还是仅在截取结果为黑时提示。

## 初步出口草案

- 建议出口：**更新 Vision + 新 epic**（用户已确认"先落一份 vision，先有份文档挺好"）。
- 判断理由：跨五个能力区域、含一个可能推翻技术栈的高风险项（浮层）、需要分批推进并在边界内反复演化规格 —— 符合 epic 而非单 issue。
- 候选事项：`001-o-v1-端到端穿刺`。目标是打通最薄的一条完整链路并证明技术风险可控，**不是**把五个区域各自做完。穿刺顺序按风险排：
  1. 热键 → 捕获 → 全屏浮层 → 拖框 → 拿到正确的物理像素矩形（唯一可能逼迫换技术栈的一步，先切）
  2. 选区位图 → leaf-ocr `/ocr` → 阅读顺序重建 → 可翻译文本（顺手验证日文假名支持）
  3. 文本 → 流式 LLM → 结果卡片显示译文 → 原文可编辑重译
  4. 精讲按需触发 → 流式 Markdown 面板
  5. 托盘、设置、DPAPI 密钥存储、剪贴板第二热键
- 暂不纳入：连续翻译 / 实时字幕、本地 ONNX 内嵌、Windows.Media.OCR 兜底、生词本、竖排、译文原位覆盖（理由见 Vision 的「探索空间」与「基础与边界」）。
