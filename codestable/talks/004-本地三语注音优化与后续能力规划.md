# 本地三语注音优化与后续能力规划

> 2026-11-14 讨论收束。用户授权将全部计划统一落盘，本期计划放第一部分。
> 本文是已确认的范围、讨论过程与后续执行安排，不代表实现已完成，也不将候选库写成既定选型。
> 总原则：绿色便携、本地离线优先；按中文、日语、英语分别由用户下载词典，保持现有部署方式。

## 第一部分：本期计划

### 1. 从“换库”回到读音准确、挂载准确与资源成本

讨论起点是[原始草稿](../../_todo_next_important.md)：中文多音字效果不足，希望升级三语词典或引擎，并控制依赖成本。

核对代码后，先纠正三个前提：

- 中文已有按词取读音的能力；当前主要不足是语境消歧依据弱，以及缺少贯穿到显示层的逐字读音映射，不能概括为完全不支持多音字。
- 现有中文词典的多字词、单字使用两档固定成本，连接矩阵很简单；同词面异读不能仅凭“交给 MeCab”就认定已实现可靠语境消歧。
- 英语运行期已经输出 IPA，并有规则词形还原；日语已有本地分词和送假名处理。新方案必须证明相对于这些现状的增益，不能把已有能力算作升级收益。

**已确认目标：** 多音字首先要在词语与上下文中读对；中文每个音节准确对应原字。替换词库只是候选手段，不能代替对选音和显示链路的修复。

### 2. 中文先完成选音、逐字对齐和多音查看

#### 先验证引擎，不预定 csharp-pinyin

草稿中的 csharp-pinyin 保留为候选，但“词频消歧、长句准确、繁简适配、约 3 MB”等描述不作为未经验证的结论或验收依据。

本期先用同一组样例比较现有方案与候选方案，核对：

- 常见多音字在不同词语中的选音，以及同词面在不同上下文中的读音；不能只测“银行／行走”这种词面本身就能区分的情况。
- 简繁文字能否使用同一套正确读音；内部若做归一化，不得改写展示、复制和收藏的原文及位置。
- 生僻字、罕见词、标点、数字、混排文字与 Unicode 扩展汉字的覆盖边界；不得拆断代理项或将未收录读音伪装成正确答案。
- 长句的选音、冷启动、批量注音与使用期间的内存开销。
- 本地离线运行、NativeAOT、词典生成与按语言分发的可行性。

原草稿的“罅缝”保留为回归样例，但先核对规范读音与期望挂载位置，再冻结金样本；不直接将草稿里的注音当作答案。

#### 将位置、默认读音与备选读音保留到 UI

目前注音区间会被转成“底字[读音]”字符串，再由显示层推断底字边界；区间位置和附加信息没有完整贯通。

本期修复应使默认读音、原文位置、字与音节的对应关系、多音候选持续可用，避免中文显示重新猜测底字范围。保留现有通用注音入口，不为未来能力先建立大而全的新架构。

中文验收要同时检查“音选对”和“挂对字”：

- 多字词的每个音节对应正确汉字；相邻未注音汉字不被误收进底字。
- 重复词、多音字连续出现、标点、换行和中外文混排时，原文位置保持正确。
- 复制原文、复制读音、复制带注音文本、选区提取、收藏、编辑再注音与缩放均不破坏对应关系。
- 维持现有短文本豁免、停用词、难词筛选和去重策略；多音提示作用于已显示的注音，不借此静默改变哪些词需要显示注音。

#### 橙色表示“存在其他读音”，不表示“本句读音不确定”

**已确认：** 中文多音字的默认注音使用橙色或主题中同含义的颜色；复用鼠标移上去hover的弹出框，允许查看其他读音。即使“银行”的“行”已经正确选为 háng，也仍可标记为多音字。同时优化hover弹出框，增加半透明、淡绿色、更现代的样式，优化文字排版缩小间距

“完整读音”的范围是所用离线词典收录的读音，不承诺穷尽所有历史、方言或罕见异读；不能凭空补出词典没有的数据。候选去重，并标出当前用于本句的读音。

以下为**目标示意**，不是已经实现的界面；示例中的省略号不代表具体候选数量：

~~~text
  yín   háng ← 多音提示色
   银     行
          │ 鼠标移上去hover注音
          ▼
       ┌─────────────────────────┐
       │ háng   ✓ 本句默认读音   │
       │ xíng                    │
       │ …词典收录的其他读音      │
       ├─────────────────────────┤
       │ 保留现有复制相关动作     │
       └─────────────────────────┘
~~~

菜单锚定目标注音，打开时不推动正文布局，不被滚动区域意外裁切，且与现有右键复制、拖动选区、左击复制读音和划词收藏气泡协调。悬停结束应恢复多音提示色，而不是统一恢复普通灰色。不能只靠颜色传达信息，菜单内也要有明确的文字标识。

本轮确认的是查看备选读音，没有确认手动纠音、修改全文或持久化个人读音偏好；这些不能作为隐含需求扩入本期。

### 3. 日语以本地 UniDic 2.1.2 做验证，通过后再替换

用户已提供本地资源：

- resources/unidic-lite@unidic-mecab-2.1.2_bin/
- resources/unidic-mecab-2.1.2_bin.zip
- resources/unidic-lite-1.0.8.tar.gz

所指目录的 README 明确说明其内容是未经修改的 UniDic 2.1.2 原版二进制文件；不能仅凭目录名将它当作裁剪后的 lite 产物。与之对应的原版 ZIP 和目录主要文件实测如下，使用十进制 MB：

| 文件 | 字节数 | 约合大小 |
| --- | ---: | ---: |
| sys.dic | 187,680,870 | 187.7 MB |
| matrix.bin | 71,544,726 | 71.5 MB |
| unidic-mecab-2.1.2_bin.zip | 46,307,109 | 46.3 MB |

**已确认取舍：** 展开后约 260 MB 的磁盘成本可以接受，不再以草稿的 15–45 MB 为前提；继续按语种分别下载，不改成基础包内置全部词典。磁盘大小可接受不等于加载内存和响应时间已经验证。

本期验证顺序：

1. 使用本地原版词典验证 LibNMeCab 对 UniDic 2.1 字段与词典格式的实际支持；现有日语使用 IPAdic 专用类型和属性，不能只替换文件。
2. 区分假名、发音、基本形与原形字段。振假名使用适合书面注音的字段，不能把音便或长音表达未经检验地当作原假名；以现有送假名和长音回归样例检查。
3. 对比现有日语金样本，以及活用、送假名、复合词、专名和未登录词。检查分词粒度变化对停用词、去重和“候选词不足 10 个”的短文本策略的影响。
4. 验证 Debug 与 NativeAOT 的词典打开、真实分词和注音，记录冷启动、首次注音、使用期间内存、闲置释放与重新加载结果。
5. 核对分发文件、许可附随材料和下载清单；原形、重音型等额外字段先验证可用性，不把“有字段”当作“已经具备整句重音分析”。

**发布职责和顺序已确认：** 先验证有效，再决定采用；确定使用后，由用户将 UniDic 替换到 ModelScope 上目前 IPAdic 所在的日语词典位置。随后同步运行期产物、下载清单／哈希、构建与打包检查、许可材料和维护文档，验证实际下载与加载。

验证通过前不改生产下载产物，不宣称已采用；采用后按新契约整体切换，不为旧 IPAdic 保留兼容分支或自动回退链。若验证未通过，记录原因并重新评估，不把失败隐藏成零结果。

日语的异读标记与读音查看不在本期，见第二部分。

### 4. 英语先保留异读数据并检查默认读音

讨论中进一步确认：英语存在同形异读，需要按整个单词及上下文理解。例如 lead 的“带领／铅”、record 的名词／动词读法；英美口音差异与语境异读也不应混为一类。

现有生成器跳过带括号编号的 CMUdict 备选项，并按小写词面保存一个 IPA；运行期同样只取一个结果。应先修复数据丢失与表达能力，不把“源词典有备选”误认为“应用已经能够在本句选对”。

**已确认本期范围：** 在英语数据设计和验证中保留备选读音，检查默认读音；橙色标记与右键列表放到后续，与日语异读交互一起规划。

MisakiSharp 保留为候选，不预定替换，也不默认其输出可不经转换直接用于学习型 IPA 显示。验证内容包括：

- 输入是否保留句子上下文，默认读音如何选择；词典、规则、模型或外部依赖分别承担什么作用。
- 读音数据是否保留全部收录候选，是否能区分不同来源的读音变体；缺少词性／词义信息时，不伪称具备完整语境消歧。
- 展示输出是否满足当前 IPA、重音、音节与长度符号口径；词形还原不应把原形读音直接误用到实际屈折词。
- 未登录词、专名、缩写、撇号与所有格的覆盖，以及离线依赖、包体、运行内存和 NativeAOT。

完整的英语语义、词性和时态消歧能力尚未被验证；本期要给出可证明的默认选音能力与已知限制，不能仅因保留多个读音就宣称已解决。

### 5. 规范标音、执行顺序与验收证据

**已确认标音口径：** 中文本期采用字词的规范标音，先解决多音字选音和逐字对应；口语连读变调不作为本期验收条件，单列后续。

本地优先是执行约束：本期注音不要求在线服务、远程密钥或联网推理；下载后的运行能力应在断网时验证。

建议按依赖推进，而不是三种引擎同时大规模替换：

| 阶段 | 实施内容 | 进入下一阶段前应有的证据 |
| --- | --- | --- |
| P0：固定基线与验证候选 | 整理三语回归样例；验证中文候选、UniDic 与英语候选；分别记录准确性、资源和 AOT 结果 | 样例有经核对的期望值；结论能区分已证实、失败与未覆盖，不凭库名或宣传定案 |
| P1：中文选音与结构化对齐 | 根据 P0 确定中文引擎；修复默认读音、位置、字音映射与备选的传递 | 多音字对照、长句、生僻字、重复词和混排样例通过；选区／复制／收藏／编辑回归通过 |
| P2：中文多音交互 | 实现多音提示色、右键候选与当前项标识；协调现有菜单和气泡 | 多音与非多音状态、悬停恢复、菜单命中、滚动裁切及原有交互均可验证 |
| P3：三语引擎与词典落地 | 日语验证通过且决定采用后完成切换；英语保留异读并检查默认读音；同步必要分发材料 | 数据不丢候选；IPA／假名口径正确；用户完成日语上传后，分语言下载、哈希和真实加载通过 |
| P4：全链路与资源回归 | 验证离线、Debug／NativeAOT、懒加载、闲置回收及重新加载 | 按代表性短文／长文记录延迟和内存；注音异常不破坏翻译与原文；实现文档按实际结果更新 |

P0 中相互独立的验证可以并行；这不授权跳过结果就替换生产数据。若候选没有证明收益，应记录未决与影响，再决定是否采用，而不是维护多套旧引擎兼容／兜底。

性能暂未约定新的数值阈值：记录当前基线与候选实测，若有明显代价或取舍，再交由用户决定。不得把下载大小、磁盘体积和进程内存混作同一指标。

本期要保留的质量证据包括：

- **正确性：** 三语金样本，中文上下文选音与字音对应，英语候选保留及默认读音，日语活用与送假名。
- **交互：** 中文多音查看可发现、可操作，不破坏复制、选区、收藏和编辑，不被容器意外裁切。
- **资源与部署：** 本地离线、NativeAOT、按语种下载、哈希与版本同步、懒加载和释放／重建。
- **可维护性：** 数据来源、实际产物、许可材料和再生流程可追溯；选型结论与已知限制一并留下。

后续实施与测试使用项目约定的 ./scripts/dev.ps1 build、./scripts/dev.ps1 test 及需要时的 -Release 路径。本轮只是讨论落盘，不运行构建或更改词典产物；也不把未测项目记录成通过。

## 第二部分：后续注音扩展

这些内容保留在后续计划中，不是本期的完成条件；下一次实施前仍需细化范围、数据来源与验收。

### 日语异读标记与读音查看

用户确认延后，但必须保留计划。日语需另行决定以词、词形还是单字组织候选，以及怎样区分语境读音与词典其他读法；不直接复制中文的“每个多音汉字都标色”规则。

UniDic 的词原形与重音型字段可在本期验证数据可用性；是否、怎样向学习者展示这些信息，尚未定案。不能将词典字段直接等同于完整语流或句子重音能力。

### 英语异读标记与右键列表

用户同意听从建议，与日语异读交互一并放到后续。使用本期保留下来的读音候选，围绕整个单词展示当前读音与其他读音；需区分语境异读、口音差异和其他变体。

释义、词性标签、手动纠音或个人偏好若要加入，需要再确认数据与交互，不在本轮隐含承诺。

### 中文口语连读变调

用户明确同意延后。后续再确定规范词典标音与实际语流读音的关系、显示方式、覆盖范围和验收样例；不与本期多音字消歧混为一个目标。

- **不提前造接口：** 本期不为这些提醒抽象统一 TTS／OCR Provider，不加云端质量优先开关、远程密钥或自动降级链。若将来真的决定做，应重新核对服务能力、隐私边界、本地与远程选择及依赖成本，不能沿用草稿里的未经验证断言。

## 最后备忘：g2pW（及 g2pM）多音消歧模型 — 仅提示，暂不采用

**来源：** 用户在 2026-11-14 要求把 g2pW 记入备忘：g2pW 号称在 pypinyin 基础上提升多音字准确率，但模型近 600+ MB，体积偏大。**仅备忘，不是选型，不是本期或下一期的承诺。**

- **g2pW：** 基于 BERT 的中文多音消歧（GitYCC/g2pW + HuggingFace YC-Chen/g2pW），依赖 onnxruntime + transformers，官方模型 ZIP 约 589 MB（561MB 级）。上个 agent 已在 `artifacts/chinese-g2pw/`（gitignore）试装依赖并下载模型，但**执行推理时导致系统卡死，未取得任何预测**，故当前没有任何准确性证据；`codestable/tools/chinese-g2pw/` 只是待运行脚手架，未验证 API 兼容性与许可。体积与本机卡死风险使其不适合作为本地离线、NativeAOT 桌面方案，除非未来能证明可裁剪/量化且稳定。
- **g2pM：** kakaobrain/g2pM 是更轻量的字符级 BiLSTM 方案（Python+numpy），`codestable/tools/chinese-defaults/probe_g2pm.py` 为只读探针但**尚未运行**；其模型体积远小于 g2pW，若未来要评估 ML 路线应优先 g2pM，而非 600MB 的 g2pW。
- **当前判断：** 优先走**纯数据词组方案**（pypinyin 词组表 + 单字频率默认 + OpenCC t2s + CC-CEDICT 合并），无 ML、约 3.3MB、可移植 NativeAOT；证据见 `codestable/tools/chinese-phrase-eval/README.md`。g2pW/g2pM 保留为「若纯数据方案在更广语料上出现明显精度瓶颈」时的备选对照，不做生产依赖。
